# HagiLight — Agent Guide

Four publishable, TypeScript-authored npm packages that provide shared Astro, Starlight, and Docusaurus components and plugins for HagiCode documentation sites. Read this before editing, building, or publishing.

## Scope and ownership

- `@hagicode/hagilight-core` — shared TypeScript utilities (links, favicon, SEO, RSS, RSS route ownership, promotions, build info via `@hagicode/hagilight-core/build-info` (browser-safe) and `@hagicode/hagilight-core/build-info-resolver` (Node-only), the site metadata contract `@hagicode/hagilight-core/site-metadata` (browser-safe) with its Node-only writer `site-metadata-writer` and the owner registry `site-metadata-ownership`, Google Analytics click-event tags via `@hagicode/hagilight-core/analytics-events`), shared `.astro` components (`Copyright`, `PromotoBanner`, `GoogleAnalytics`, `PostHog`, `Analytics51LA`), and brand assets. No Starlight dependency.
- `@hagicode/hagilight` — plain-Astro integration (`hagilight`, which generates sitemap, robots.txt, and RSS feeds by default, plus the `rss` option for customization), `hagilightFavicon`, `Footer`, `SEOHead`, and generated routes. Depends on core only.
- `@hagicode/hagilight-starlight` — Starlight plugin (header, footer links, locale chooser, content-width control, theme picker with three extra light/dark themes and a Forest first-visit default, 404 hero, RSS, analytics, AI disclosures). Depends on core only.
- `@hagicode/hagilight-docusaurus` — Docusaurus 3 plugin (`hagilightDocusaurus()`): footer, promotion banner, analytics, SEO head tags and JSON-LD, sitemap/robots/RSS discovery, and the locale catalog at `./locales`. Depends on core only; peers `@docusaurus/core` and `@docusaurus/theme-classic` `^3.9.2`.
- By default this repository is **documentation-maintenance scope** for agent edits: modify `AGENTS.md` as instructed and treat source, generated, and cache files as read-only unless the user expands scope.

## Commands

```sh
npm install                 # install all workspaces
npm run build              # tsc -b: compile packages/*/src to packages/*/dist (core first)
npm run typecheck          # build + check Astro route files and test/types fixtures
npm test                   # build, then run node --test on test/*.test.mjs
npm run build:example      # build packages, the core-footer demo, and the Starlight demo variants, then verify their output (the Docusaurus demo is built and checked by `npm test`)
npm run build:starlight-example  # build only the default Starlight demo (what demo-starlight-web.yml deploys)
npm run build:docusaurus-example  # build the Docusaurus demo alone
npm run pack:check         # verify the tarball contents (scripts/verify-pack.mjs)
npm run integration:installed  # validate an installed tarball (scripts/integration-installed.mjs)
npm run test:viewport      # Playwright desktop viewport regression plus RootTransit browser check (needs Chromium; run in CI on Linux)
```

## Architecture

- npm workspaces: `packages/*` and `examples/*`.
- TypeScript sources live in `packages/*/src/*.ts` and compile (strict, `tsconfig.base.json`) to ignored `packages/*/dist/` ESM + `.d.ts`. `.astro` components and Astro route `.ts` files stay at each package root and import `./dist/*.js`. Every JS export uses `types`/`default` conditions.
- `packages/core/` — shared runtime, components, and assets used by both feature packages. Localized footer catalog lives in `packages/core/src/related-sites.json` (keep in sync with Docs). The footer's product statement (headline, summary, three pillars, Download/Product Docs CTAs) is `FooterBrand.astro` with copy from `src/footer-brand.ts` (`@hagicode/hagilight-core/footer-brand`); the `RootTransit.astro` root redirect page resolves its destination through `src/root-transit.ts`.
- Comparison article data (`packages/core/data/comparison-articles/<locale>/<slug>.json`, shipped in the core tarball): core owns the `*-vs-hagicode` article JSON and its contract. `@hagicode/hagilight-core/comparison-articles` (`src/comparison-articles.ts`) is browser-safe: types, `validateStructuredArticleDetail`, path builders and manifest builders over loaded details. `@hagicode/hagilight-core/comparison-articles-source` (`src/comparison-articles-source.ts`) is Node-only: it lists and loads the packaged files relative to the module location, never the working directory. `@hagicode/hagilight-core/comparison-articles-data/<locale>/<slug>.json` is the raw JSON export. The contract tests live in `test/comparison-article-content.test.mjs` and `test/comparison-articles.test.mjs`. `repos/index` consumes this data and no longer keeps a copy.
- Body-image plugin (`packages/core/src/content-images.ts`, subpath `@hagicode/hagilight-core/content-images`): core owns the transform, which gives body `<img>` lazy/async loading and the `hagilight-content-image` marker outside `<picture>`. Both feature packages' `hagilight()` register it through `registerContentImages` on the Markdown processor (Sätteri `hastPlugins` or unified `rehypePlugins`), and `checkContentImageRegistration` warns once if the processor dropped it. Their `contentImages` option opts out; registration never depends on integration order or on `enabled`.
- `packages/astro/` — plain-Astro integration (`src/integration.ts`), Footer, SEOHead, and route entry points.
- `packages/starlight/` — Starlight-only overrides and the plugin in `src/index.ts`. New auto-applying components get an `exports` entry and are registered in `src/index.ts`. It must import shared code from core, never from `@hagicode/hagilight`.
- `packages/docusaurus/` — Docusaurus plugin: `src/index.ts` (plugin lifecycle and client modules), `src/options.ts` (option validation and defaults), `src/discovery.ts` (sitemap, robots.txt, RSS), `src/analytics.ts`, `src/seo.ts`, `src/warnings.ts`, `src/locales.ts`, the theme swizzles under `src/theme/` (`Footer`, `SiteMetadata`), and the browser modules `src/client/promoto.ts`, `src/client/promoto-markup.ts`, and `src/client/analytics.ts`. It imports shared code from core, never from the Astro or Starlight packages.
- HagiCode showcase (`packages/starlight/ArticlePromotion.astro`): the per-locale copy catalog lives in `packages/starlight/src/article-promotion-copy/` (ten locale modules, a glossary, and a frozen `COPY`; also exposed read-only as `@hagicode/hagilight-starlight/showcase`), and its audited images and provenance record live in `packages/starlight/assets/showcase/` (shipped sources are WebP and SVG within a 768 KiB total budget, 200 KiB per raster and 8 KiB per SVG; the site delivers each raster as AVIF, then WebP, then JPEG, derived at its own build; never hot-linked). It includes a Windows download button that uses the official Microsoft Store badge (`src/windows-download.ts`) with a static Store link fallback; the badge loader from `get.microsoft.com` is the only script. Keep the copy, the images, and the badge product id in sync with `repos/web` and `repos/docs` (read-only references), and see the package README for the audit and refresh procedure.
- `examples/demo-starlight-web/` — private Starlight demo exercising both package entry points.
- `examples/demo-web/` — private core Astro demo without Starlight.
- `examples/demo-docusaurus-web/` — private Docusaurus 3 demo exercising the plugin and the locale catalog; its build output is `build/`.
- `scripts/` — `packages.mjs` (package order and version-graph checks), `verify-pack.mjs`, `integration-installed.mjs`, `publish.mjs`, `release.mjs` (publishing/release helpers).
- `test/` — node:test suites covering exports, site links, header, language chooser, promotions, RSS ownership, AI disclosures, article promotion, Docusaurus options and discovery, and release logic; `test/types/` holds typed consumer fixtures with `@ts-expect-error` negative cases.

## Conventions

- All four packages share one version; every feature package depends on the exact core version. Publish core first, then `@hagicode/hagilight-docusaurus`, `@hagicode/hagilight`, and `@hagicode/hagilight-starlight` (`scripts/publish.mjs` enforces this order).
- Confirm `@hagicode` scope permission before first publish.
- The plugin rejects a site that already overrides `Footer` or `components.Header`; do not silently replace consumer overrides. The Docusaurus plugin only warns (`src/warnings.ts`) when `src/theme/Footer` exists while `footer` is enabled, or when `src/theme/SiteMetadata` exists while `seo` is enabled.
- Default IDs, shared by the three feature packages: Google Analytics `G-EN03FMT2Q4`, 51LA `L6b88a5yK4h2Xnci`; both load only on production pages. Docusaurus sites get these defaults unless they set their own IDs.
- PostHog: shared browser-safe generator `@hagicode/hagilight-core/posthog` and production-only component `@hagicode/hagilight-core/PostHog`. Defaults: `phc_qiVVihsL925ovhPYNdLJWz4k7aoKVMwYCevgZPE6PER5`, API host `https://us.i.posthog.com`, and SDK defaults `2026-05-30`. Starlight and Docusaurus enable it when options are omitted, including `analytics: {}`; supplied `{}` disables it, `{ enabled: true }` requires `apiKey`, and `{ enabled: false }` opts out, matching Google Analytics. Render once in the global head alongside GA; Starlight includes PostHog on 404 pages and treats a site-owned Head as a conflict until SEO, GA and PostHog are disabled. Plain Astro consumers compose `<PostHog />` without props in their layout head (the demo also uses the transit page head slot). Keep the supplied loader unchanged, one initialization per document, and SDK-owned navigation; add no npm dependency, capture calls or route listeners. Update loader, provider, development-rendering, generated-output, type and pack checks when changing this contract.
- Google Analytics click events: tracked links are declared in `TRACKED_SITE_LINKS` (`packages/core/src/analytics-events.ts`); the id is the `event_label`, so renaming a link id changes its GA label and fails the inventory snapshot in `test/analytics-events.test.mjs` until the change is deliberate. Every tagged link goes through `gaEventAttributes()` or `siteLinkGaAttributes()` (never hand-written `data-ga-*` in `.astro` files), and related sites, RSS, sitemap, about, contact, filings, and consumer `extraLinks` stay untagged. When the tracked set, vocabulary, or parameters change, update the core README and the mono root Google reference too.
- Cross-repo Google Analytics rules (initialization, event vocabulary, change checklist, verification) live in `docs/google-analytics-integration-reference.md` in the hagicode-mono root; this repository's core README stays the API reference.
- Site metadata file: every integration writes `.well-known/hagilight.metadata.json` (`SITE_METADATA_PATH` in core is the only place the path is spelled) with `schemaVersion: 1`. Core owns the schema, the builder, the validator and the serializer; packages only collect facts. Only booleans for analytics leave the build, never IDs or keys. `metadata: false` opts out, and a site-owned copy in `public/` or `static/` is never overwritten. Plain Astro and Starlight coordinate through `site-metadata-ownership`: Starlight owns the file when enabled, and plain Astro defers. Docusaurus writes from the default-locale build only. The file is written last, after the sitemap and `llms.txt`, through an integration appended during setup, because Astro runs build hooks in list order. Docs, schema changes, and the README example (checked by `test/site-metadata.test.mjs`) must move together.
- Build info: `@hagicode/hagilight-core/build-info-resolver` is Node-only (it runs Git and reads `process.env`). Modules the Docusaurus client bundle imports (`packages/docusaurus/src/theme/**` and `src/client/**`) import only `@hagicode/hagilight-core/build-info`, never a `node:` module or the resolver. Only `packages/docusaurus/src/index.ts` calls the resolver, on the Node side of the plugin lifecycle.

## Testing

- `npm test` builds the packages, then runs `node --test test/*.test.mjs`.
- Run tests after any change to link resolution, header/language logic, theme picker logic, promotions, AI disclosures, Google Analytics click events, or body-image handling.
- `npm run build:example` must succeed as a consumer integration check. It builds four Starlight configurations (default; blog-only with a base path; unified processor plus `hagilight()` discovery; promotion off plus `contentImages` opt-out) and checks the body images of each. The RSS include filters are unit-tested, not built.

## Deployment / Publishing

- The `demo-*.yml` deploy workflows only build and publish their own demo (`build:starlight-example`, `build:core-footer-example`, `build:docusaurus-example`); the multi-variant verification in `build:example` runs in CI, not on deploy.
- CI (`.github/workflows/ci.yml`) type-checks all four packages and runs `npm test` (which includes real Astro and Docusaurus demo builds) on Linux, Windows, and macOS; the OS-independent `build:example`, pack checks, installed-tarball consumers, and viewport regression run on Linux only. `npm-publish.yml` repeats only type-check and test, then packs and installs the stamped tarballs.
- `npm-publish.yml` uses npm OIDC provenance (no token) with npm trusted publishers: owner `HagiCode-org`, repo `hagilight`, workflow `npm-publish.yml`. Configure trusted publishers before enabling publication; an initial authorized publish may be required first.
- Every push to `main` publishes a unique `dev` dist-tag prerelease; a GitHub release with a `vX.Y.Z` tag publishes all four packages to `latest` (core first; existing versions are skipped).
- `.github/workflows/demo-web.yml` publishes `examples/demo-web/` to the `demo-web` branch and creates the `demo-web` GitHub deployment with `https://hagilight.hagicode.com/`; select `demo-web` root as this repository's GitHub Pages source instead of `gh-pages`. The branch is force-pushed as one latest commit (`force_orphan: true`, with `CNAME` and `.nojekyll` kept) on every publish, so it is not a rollback source; roll back by reverting the offending source commit on `main`.
- `.github/workflows/demo-starlight-web.yml` publishes `examples/demo-starlight-web/` to the `demo-starlight-web` branch and creates the separate `demo-starlight-web` GitHub deployment with `https://hagistar.hagicode.com/`; that domain requires a separate hosting consumer because this repository's GitHub Pages source serves only one branch. Like `demo-web`, the branch is force-pushed as one latest commit (`force_orphan: true`, with `CNAME` and `.nojekyll` kept) on every publish, so it is not a rollback source; roll back by reverting the offending source commit on `main`.
- `.github/workflows/demo-docusaurus-web.yml` publishes `examples/demo-docusaurus-web/build` to the `demo-docusaurus-web` branch and creates the separate `demo-docusaurus-web` GitHub deployment with `https://docusaurus.hagicode.com/`. Like the other demo workflows, the branch is force-pushed as one latest commit (`force_orphan: true`, with `CNAME` and `.nojekyll` kept), so it is not a rollback source; roll back by reverting the offending source commit on `main`. That domain requires a separate hosting consumer, as `hagistar.hagicode.com` does.
- A successful deployment means its workflow built the example and published its branch; it does not verify that the separate Starlight host has consumed the snapshot or that either site is reachable.
- All three demo workflows run independently on pushes to `main`; none updates `gh-pages`.
- `release-draft-action.yml` maintains the next stable draft through `HagiCode-org/hagi-release-drafter@v0.1.2`, from Conventional Commit messages since the latest `vX.Y.Z` tag (no PR labels needed, direct pushes to `main` are included). A feature bumps the minor, a breaking change bumps the minor while 0.x (major afterwards), anything else bumps the patch; run the workflow manually with the `version` input to override. Publishing the draft triggers `npm-publish.yml`.
